Fintech Test Automation Framework

Playwright + TypeScript framework covering API and UI testing for the User and Transaction services, with a mock backend built to exercise it against.

Stack: Playwright, TypeScript, Express Scope: API suite, UI suite, utilities, reporting Repo: qe-take-home-assessment/

01 API Test Suite

Tests run against a small Express mock of the two services described in the brief — POST /api/users, GET /api/users/:id, POST /api/transactions, GET /api/transactions/:userId — backed by an in-memory store that resets between tests.

CRUD operations

  • Create a user and confirm the response shape and field values users.api.spec.ts
  • Fetch a user by id, including the 404 path for an unknown id
  • Create transfer, deposit, and withdrawal transactions transactions.api.spec.ts
  • List a user's transactions — empty list, multiple results, and isolation between users

Error scenario handling

  • Duplicate email on user creation → 409
  • Transaction against an unknown userId or recipientId → 404
  • Transfer submitted without a recipientId → 400

Data validation

  • Missing name, malformed email, invalid accountType all rejected with 400 + field detail
  • Zero or negative transaction amount rejected with 400
  • Invalid transaction type rejected with 400

Authentication / authorization

  • Request with no x-api-key header → 401
  • Request with an invalid key → 403
  • Checked on both the user and transaction endpoints

02 UI Test Suite

A minimal static frontend (plain HTML + JS, no framework) stands in for the real one, giving Playwright actual pages to drive instead of testing against fixtures.

User registration flow

  • Fill the form, submit, and confirm the success message renders registration.ui.spec.ts
  • Submitting a duplicate email surfaces the server's error text in the UI
  • Leaving a required field empty triggers native browser validation

Transaction creation flow

  • Successful transfer and deposit both show a confirmation message transaction.ui.spec.ts
  • Unknown userId or recipientId shows the error message from the API

Error message validation

Every negative-path test asserts on the actual text rendered in the error banner, not just that an error element exists — so a regression that swaps in the wrong message fails the test.

04 Reporting

Test results — multiple formats

Configured in playwright.config.ts:

  • list live output in the terminal while the run is in progress
  • html interactive report at playwright-report/index.html
  • json machine-readable results at test-results/results.json

Screenshots for UI failures

screenshot: 'only-on-failure' in the Playwright config captures the page automatically whenever a UI test fails; two of the UI tests also take an explicit screenshot at the error state for the report.

API response logging

tests/utils/logger.ts writes each logged API call — status, headers, body — to its own JSON file under test-results/api-logs/, so a failing assertion can be traced back to the exact response that caused it.

— Running It End to End

One command handles the whole flow — Playwright starts the mock server, waits for it to be healthy, runs the suite, and shuts it down.

npm install
npx playwright install chromium
npm test
1Playwright's webServer hook runs npx ts-node mock-server/server.ts and polls /health until it responds.
2Each test's beforeEach calls POST /api/test-utils/reset so the in-memory store starts clean.
3API specs hit the endpoints directly through ApiClient; UI specs load the static pages and drive them through the browser.
4Reports and logs land under playwright-report/ and test-results/ once the run finishes.

Narrower runs:

npm run test:api    # API suite only
npm run test:ui     # UI suite only
npm run report      # open the last HTML report
